# Formal Verification Plan — v0.01

## Project

Self-Similar Calabi–Yau Visualizer

Formal verification namespace: `formal-v0.01`

## Thread rule

Each formal-verification thread closes exactly one verifiable milestone. No later mathematical stage may be implemented inside an earlier bootstrap thread.

## Responsibility split

The existing JavaScript/Node stack remains authoritative for runtime behavior: JSON schema validation, validation-before-render ordering, DOM state, base renderer state, one-step pullback state, request-bounded lazy expansion, immutability, and no eager materialization.

Lean/mathlib is introduced as a separate mathematical formalization layer. Passing F01 means only that the **formal verification toolchain bootstrap passed**. It does not mean that project mathematics has already been formally verified.

## F01 acceptance gates

The milestone is accepted only if all of the following execute successfully in the actual project environment:

```bash
cd formal
lake update
lake exe cache get
lake build
lake env lean SelfSimilarCY/Basic.lean
```

The generated `lake-manifest.json` must record the exact mathlib commit above and must not replace mathlib with a local path dependency.

After the Lean build, the four historical JavaScript verifiers must still pass:

```bash
node verify_scene_spec_v0_03.js
node verify_base_renderer_v0_04.js
node verify_one_step_pullback_v0_05.js
node verify_recursive_lazy_expansion_v0_06.js
```

The following JavaScript syntax checks must also exit successfully:

```bash
node --check scene-spec.js
node --check base-renderer.js
node --check one-step-pullback.js
node --check recursive-lazy-expansion.js
node --check app.js
```

Browser runtime execution is not an F01 gate and remains separately tracked as `not_tested` unless explicitly run.
